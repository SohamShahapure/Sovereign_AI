## 1. How to run

```bash
uv run python scripts/download_docs.py
```

```bash
uv run python -m rag.index
```

```bash
uv run python -m rag.search "What dividend did HDFC Bank recommend for FY2025-26?"
```

`rag.index` deletes and recreates the collection every time, so it always rebuilds from scratch. It
only deletes the old collection *after* all embeddings are computed, so a crash halfway leaves the
previous index usable. Options: `--docs <file> ...` to index a subset, `--no-header` to embed chunks
without the company header (for the Days 9–10 comparison).

Outputs (git-ignored):
- `qdrant_storage/`: the Qdrant collection `annual_reports` (local mode).
- `data/processed/chunks.jsonl`: every chunk with its metadata. BM25 (Days 11–12) and the eval-set
  tools (Days 7–8) read this instead of re-parsing PDFs.
- `data/processed/index_manifest.json`: model, settings, counts and timings of the last build.

**Windows note:** the `pytest.exe` and `ruff.exe` launchers in `.venv\Scripts` were blocked by an
Application Control policy (Smart App Control) after `uv add` regenerated them. Run them through
Python instead: `uv run python -m pytest`, `uv run python -m ruff check .`.

## 2. Pipeline

```
data/raw/*.pdf
   │  rag/parse.py   PyMuPDF text blocks in PDF order; spreads (> 1000 pt wide) split into L/R
   │                 halves; running headers/footers removed; hard line breaks unwrapped
   ▼
printed pages  (doc, pdf page, half, page label, text)
   │  rag/chunk.py   ≤ 450 BGE tokens per chunk, 64-token overlap, never crossing a page;
   │                 "<Company> — Annual Report FY2025-26" header added to the embedded text
   ▼
chunks  (chunk_id, doc, page, half, label, company, text, n_tokens)
   │  rag/embed.py   BAAI/bge-small-en-v1.5 ONNX, [CLS] vector, L2-normalized (384-d)
   ▼
Qdrant collection "annual_reports"  (cosine distance; payload = chunk metadata + text)
```

**Chunk ids** look like `sbi_ar_2025-26:p0201:c0` (doc, 1-based PDF page, spread half if any,
chunk number on that page). Qdrant point ids are `uuid5(chunk_id)`, so the same chunk gets the same
id on every rebuild.

## 3. Design decisions and trade-offs

| Decision | Why | Trade-off |
|---|---|---|
| **PyMuPDF, block order (`sort=False`)** | Annual reports are multi-column. `sort=True` orders lines only by height and interleaved two columns line by line; the PDF's own block order follows the columns. Also opens the encrypted HCLTech PDF without extra packages. | Relies on the PDF being authored in reading order (true for all 11 here) |
| **Split pages wider than 1000 pt** | Reliance, Asian Paints and Airtel are almost all two-page spreads; SBI, Tata Steel and Wipro partly. One unit = one printed page, so a chunk never mixes two unrelated pages. 1000 pt is wider than A4 landscape (842), so rotated tables stay whole. | A true fold-out graphic gets cut in half (a handful of HDFC/Kotak pages) |
| **Remove repeated blocks in the top/bottom 8% of the page** | Running headers ("HDFC Bank Limited Integrated Annual Report 2025-26"), page numbers and SBI's section nav bar appear on hundreds of pages and add nothing. A block is removed only if it is in the edge band *and* repeats (digits ignored) on ≥ 15% of the report's pages, so repeated table numbers in the body survive. | A real one-line footnote that repeats in the footer band would be dropped |
| **≤ 450 tokens per chunk** (not 500–800) | BGE reads at most 512 tokens and silently ignores the rest. An 800-token chunk would be represented by its first ~510 tokens only. 450 leaves room for the context header. Counted with BGE's own tokenizer. | More chunks than an 800-token setup; long tables get split |
| **64-token overlap** | A sentence or table row cut at a chunk boundary still appears whole in one of the two chunks | ~15% more text to embed |
| **Chunks never cross a page** | Each chunk cites exactly one page, which retrieval hit@5 (Days 9–10) checks against `source_page` | Short pages become short chunks (pages under 20 tokens are dropped) |
| **Company/year header in the embedded text only** | Three banks write near-identical sentences ("net interest income grew…"). Without the company name, the vector can't tell them apart. The stored `text` stays clean for the LLM and citations. `--no-header` lets Days 9–10 measure the effect instead of assuming it. | Header tokens slightly dilute short chunks |
| **bge-small-en-v1.5 (384-d)** | Measured on this laptop's CPU: ~2.5× faster than bge-base. A full rebuild is ~20 min instead of ~1 h. Changing `EMBED_MODEL` and rebuilding is all it takes to try bge-base later. | Somewhat lower retrieval quality than bge-base on benchmarks; to be measured in Days 11–12 |
| **onnxruntime directly, not fastembed** | Same vectors (cosine 1.00000), but fastembed ran ~2 chunks/s on real chunks and direct onnxruntime with length-sorted batches ~9.4/s on this machine. Also avoids PyTorch (~1 GB). | A few lines of model code to own (tokenize → run → [CLS] → normalize) |
| **BGE query instruction** | BGE v1.5 is trained with `Represent this sentence for searching relevant passages: ` on the query side only | — |
| **Qdrant local mode** | Docker isn't installed on this machine. `QDRANT_URL` switches to a Qdrant server with no code change. | Local mode is single-process (one client at a time) and brute-force; fine at ~10k points |

## 4. Embedding speed on this machine (i5-13420H, CPU only)

Measured with 512-token inputs (raw onnxruntime) and with real chunks (rag.embed):

| Setup | Throughput |
|---|---:|
| fastembed, bge-small, real chunks, batch 16 | ~2 chunks/s |
| onnxruntime direct, bge-small, 16 × 512 tokens, all threads | 7.1 seq/s |
| onnxruntime direct, bge-base, 16 × 512 tokens, all threads | 2.8 seq/s |
| onnxruntime direct, bge-small, 1 thread | 3.1 seq/s |
| **rag.embed, bge-small, real chunks, length-sorted batches of 16** | **9.4 chunks/s** |

What this shows: compute is the limit (bge-base is ~2.5× slower than bge-small, as its size
predicts), threads scale poorly beyond ~4 on this hybrid P/E-core CPU, and sorting chunks by length
before batching wins back the time otherwise spent on padding. These are dev-machine numbers for
choosing a setup, not project benchmarks (no `bench/results/` file).

## 5. Known limitations

- **Tables are flattened** into lines of cells. Numeric questions on big tables may retrieve the
  right page but give the LLM hard-to-read text. Revisit if the eval shows numeric questions failing.
- **No OCR.** 20 Bajaj Auto pages (and a few others) are image-only and produce no text.
- **The rupee sign** comes out as another glyph in some PDFs (Reliance `(I in crore)`, SBI
  `(` Crore)`), because of how their fonts encode it. Numbers are unaffected.
- **Fold-out graphics** wider than 1000 pt get split down the middle.
- **Some running headers survive.** Wipro's header changes by section ("…STATUTORY REPORTS AND
  FINANCIAL STATEMENTS CONSOLIDATED FINANCIAL STATEMENT UNDER IND AS"), so no single version repeats
  on 15% of pages. It shows up at the start of many Wipro chunks as noise.
