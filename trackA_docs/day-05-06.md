## 1. How to run

```bash
uv run python -m uvicorn rag.api:app --port 8080
```

```bash
curl -s localhost:8080/health
```

```bash
curl -s localhost:8080/ask -H "Content-Type: application/json" -d '{"question": "What final dividend per share did HDFC Bank recommend for FY2025-26?"}'
```

Port 8080 avoids clashing with a local vLLM on 8000. Start it with `python -m uvicorn`, because
Smart App Control blocks the `uvicorn.exe` launcher on this machine, as it does `pytest.exe`.
Ollama must be running, and the index must already be built (`python -m rag.index`).

## 2. What a request does

```
POST /ask {"question"}
  │ Retriever.search      embed question (BGE + query instruction) → top-5 chunks from Qdrant
  │ build_messages        system rules + sources "[n] <Company>, annual report FY2025-26, page <p>"
  │                       added in rank order while they fit CONTEXT_BUDGET_TOKENS (3000)
  │ rag.llm.chat          POST {LLM_BASE_URL}/v1/chat/completions, temperature 0, max_tokens 384
  │ extract_citations     keep only sources the answer cites, renumber [n] to match
  ▼
{"answer", "citations": [{"doc", "page", "chunk_id"}], "latency_ms", "model"}
```

- `page` is the 1-based PDF page index, per the contract change request in CLAUDE.md (not yet
  agreed with Track B).
- `latency_ms` is measured on the server, from receiving the question to having the answer.
- Errors: empty question → 422. LLM timeout → 504. LLM unreachable or error → 502. Empty index →
  503 on both `/ask` and `/health`. Contract 3.2 only defines the healthy `/health` reply, and an
  API with no index shouldn't claim to be healthy.

## 3. Design decisions and trade-offs

| Decision | Why | Trade-off |
|---|---|---|
| **Return only the sources the answer cites**, renumbered so `[1]` = `citations[0]` | Returning all 5 retrieved chunks would claim support the answer may not have, and Days 9–10 score faithfulness against `citations` | If the model forgets to cite, `citations` is empty even when the answer is right. The eval will show how often. |
| **Fixed "not found" sentence** (`I could not find this in the provided annual reports.`) | "Not in the documents" questions can be scored by exact match, and the model has an explicit way to say no instead of guessing | Wording is fixed in `rag/prompt.py` (`NOT_FOUND`) |
| **Context budget enforced by us** | Ollama runs llama3.1 with a **4,096-token** context and the OpenAI-compatible endpoint can't change it per request. Past that, the oldest tokens (the instructions) are cut silently. Sources are added in rank order until 3,000 tokens, so trimming always drops the least relevant ones. | Counted with the BGE tokenizer as a stand-in for Llama's. Llama 3's bigger vocabulary uses fewer tokens, so this errs on the safe side: 5 sources came to 2,076 real prompt tokens. |
| **temperature 0** | Same question → same answer, so eval runs are repeatable and comparable | Slightly less fluent wording |
| **Copy numbers exactly, with units** (prompt rule) | Most eval questions are numbers. Rounding or unit changes would fail exact/numeric matching. | — |
| **One Qdrant client per process** | Local mode loads all 10,972 vectors when it opens, so it can't happen per request. Searches are serialized with a lock in local mode, which isn't built for concurrent use; with `QDRANT_URL` set there's no lock. | In local mode only one search runs at a time. It takes milliseconds, so the LLM call is the real bottleneck. |
| **Sync `def` endpoint** | FastAPI runs it in its thread pool (40 threads by default), so a slow LLM call doesn't block `/health` or other requests | For the 50-user load test in Day 14, the thread pool and the LLM server's batching set the ceiling |
| **Model and Qdrant loaded at startup** | The first request isn't slowed by loading the ONNX model and the index | ~2 s startup |

## 4. Live check (2026-11-07, Ollama llama3.1 8B Q4_K_M on CPU)

| Question | Answer (abridged) | Citations | Checked against source | Latency |
|---|---|---|---|---:|
| What final dividend per share did HDFC Bank recommend for FY2025-26? | ₹13.00 per equity share | HDFC p.251, p.509, p.377 | ✅ all three pages state ₹13.00 | 73 s |
| What was Infosys's consolidated revenue in FY2025-26? (not in the set) | "I could not find this in the provided annual reports." | none | ✅ correct refusal; Wipro/HCLTech pages were in its sources but weren't used | 62 s |
| Compare the standalone PAT of Tata Steel and Bajaj Auto for FY2025-26 | ₹16,065 crore vs ₹9,825 crore, difference ₹6,240 crore | Tata Steel p.235, Bajaj Auto p.37 | ✅ both figures match, arithmetic correct | 104 s |

The first request used **2,076 prompt tokens and 30 answer tokens**, so on CPU almost all of the
~70 s is the model *reading the prompt* (~30 tokens/s), not writing. That's the part a GPU server
(Track B's vLLM) speeds up most. Locally, `RETRIEVAL_K` or the chunk size trades latency against
recall.

These are three hand-checked examples, not an eval and not a benchmark (no `bench/results/` file).
The 100-question eval in Days 7–10 gives the real numbers.

## 5. Known limitations

- **CPU latency is 1–2 minutes per question.** Fine for building the eval, too slow for a demo or
  load test. Those happen at integration on Track B's GPU.
- **Rupee sign:** some PDFs encode ₹ as `` ` `` or `I`. The model usually writes ₹ back, but
  exact-match scoring should normalize currency symbols.
- **The 4,096-token context is an Ollama default,** not a model limit. At integration, vLLM's
  `--max-model-len` decides it, and `CONTEXT_BUDGET_TOKENS` can grow.
